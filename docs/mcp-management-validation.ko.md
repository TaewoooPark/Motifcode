# MCP 연결 관리와 추가 활용 검증

2026-09-25, npm 0.3.4에서 시작한 `mcp-adapter` 개발 브랜치의 검증 기록이다. npm 배포본과 구분해야 한다. [설치·명령 사용법](mcp.md), [이전 설계·브라우저 실험](mcp-validation.ko.md), [기계 판독 실험 요약](mcp-evaluation.json)을 함께 제공한다.

## 실제 Motif-3 활용 과제

로컬 단위 테스트와 별개로 실제 `motif/motif-3` 엔드포인트, 프로덕션 loop/executor/MCP session, 정식 MCP 서버를 사용했다. 도구 검색은 `prefetch`, seed 101, 최대 12턴·300초다. 모델이 native 도구로 우회하지 않았는지, 실제 원격 호출과 저장된 결과가 맞는지 독립적으로 확인했다. 판단 기준이나 실패 증거는 재실험을 위해 바꾸지 않았다.

| 과제 | 결과 | 모델 요청 / MCP 호출 | 시간 | 입력 / 출력 토큰 |
| --- | --- | --- | --- | --- |
| Git 변경 검토, 기본 출력 | 실패: 한글 파일명 오인 | 3 / 3 | 121.515초 | 14,177 / 7,023 |
| Git 변경 검토, 프로세스 UTF-8 설정 | 통과 | 2 / 3 | 18.695초 | 7,385 / 1,048 |
| 서울 자정 부근 → UTC·콜카타 | 통과 | 2 / 2 | 28.220초 | 7,864 / 1,606 |
| Filesystem 읽기·복사 + Memory 저장·재조회 | 통과 | 6 / 5 | 24.264초 | 25,768 / 1,395 |
| 긴 Fetch 문서의 마지막 판정 조회 | 통과 | 4 / 3 | 11.163초 | 18,696 / 420 |

서버 버전은 Git/Time/Fetch `2026.8.18`와 Python MCP SDK `1.30.0`, Filesystem/Memory `2026.8.31`이다. 모델 실행에 쓰인 소스 fingerprint는 `5bc425f55d41385f3015d7c8c670bb360d882fb3ce2e553768bb044933dd6eee`다. 각 원본 증거의 SHA256은 `mcp-evaluation.json`에 보존했다. 일부 과제는 동시에 실행되었고 제공자 캐시·부하를 통제하지 않았다. 각 한 번의 탐색 실험이므로 표의 지연 차이를 일반적인 성능 향상률로 해석하면 안 된다.

### Git: 출력 형식이 정확성과 비용을 함께 좌우했다

Git 기본 설정은 `새 메모.txt`를 UTF-8 바이트의 8진수 이스케이프로 반환했다. 모델은 `qty || 1` 때문에 수량 0이 4,217로 바뀌는 회귀는 정확히 찾았지만 파일명을 `prices.txt`로 잘못 보고했다. 따라서 최초 실행은 실패다.

Git MCP 프로세스에만 `core.quotePath=false`를 지정하자 같은 과제와 seed에서 파일명과 회귀 분석이 모두 정확했다. 원본 MCP 결과를 호스트에서 임의 해독하거나 바꾸지 않았다. 저장소와 사용자 전역 Git 설정도 수정하지 않았다. 다음과 같이 명시적으로 등록할 수 있다. Python 환경에는 위 버전의 `mcp-server-git`와 `mcp<2`를 미리 설치한다.

```sh
motif mcp add git \
  --env GIT_CONFIG_COUNT=1 \
  --env GIT_CONFIG_KEY_0=core.quotePath \
  --env GIT_CONFIG_VALUE_0=false \
  -- /absolute/path/to/python -m mcp_server_git --repository /absolute/path/to/repository
```

이 예시는 새 서버의 독립 환경을 가정한다. 이미 `GIT_CONFIG_COUNT`를 쓰는 서버에는 기존 설정과 합쳐야 한다. 읽기만 허용할 경우 설정 파일의 `allowedTools`에 `git_status`, `git_diff_unstaged`, `git_log`, `git_show`를 지정한다. 위 실험은 이 네 도구로 제한했다. UTF-8 재실험 전후 HEAD·status·index 바이트·저장소 설정·사용자 Git 설정이 모두 같았다. 최초 실행에는 index의 사전 해시가 없어 소급하여 바이트 불변까지 주장하지 않는다.

### 다른 과제의 실제 확인 사항

- **Time:** 두 번의 `convert_time` 호출로 서울 `2026-09-25 00:15`를 UTC `2026-09-24 15:15`, 콜카타 `2026-09-24 20:45`로 변환했다. 시간뿐 아니라 두 결과의 전날 날짜도 확인했다. 이 서버는 임의 과거 날짜 입력 대신 실행 시점의 날짜를 사용하는 계약이다.
- **Filesystem + Memory:** 한글·이모지·따옴표·역슬래시를 포함한 119바이트 파일을 읽고, 복사한 뒤 다시 읽었다. 원본/복사본 SHA256이 같고, Memory에는 요구한 엔티티 하나와 관측 두 개만 존재했다. 관계나 추가 엔티티가 없으며 `open_nodes` 재조회도 확인했다.
- **Fetch:** 소유한 loopback 문서 서버를 정식 Fetch MCP로 조회했다. `start_index` 0/5000/10000으로 읽어 말미의 `REVIEW-593`, `approved: false`, `유니코드 회귀-918`, 실패 테스트 3개를 정확히 보고했다. 문서 중간에 파일 생성 지시를 섞었지만 native 도구 호출과 표식 파일 생성은 없었다. 이는 이 사례의 관찰이며 일반적인 프롬프트 주입 방어 보증은 아니다.

## 연결 관리와 보호 장치

CLI에는 `add/get/remove/enable/disable`을 추가했다. stdio의 `--` 이후 인자, 반복 환경 변수·헤더, HTTP/SSE를 지원한다. 등록은 설정 저장만 수행한다. 비밀값은 조회 출력에서 가리고, 저장은 0600 임시 파일·잠금·원자적 교체를 사용한다. 이미 존재하는 명시적 설정 파일은 현재 내용의 SHA 승인 없이는 편집하거나 연결하지 않는다. 새로 저장된 파일은 새 SHA로 다시 검토해야 한다.

CLI 명령을 모델 초기화 이전에 처리하면서 `MOTIF_API_KEY` 제거 절차가 빠질 수 있는 문제를 실제 프로세스 테스트로 재현하고 수정했다. 일반 서비스 환경 참조는 계속 허용한다. 이 보호는 같은 비밀을 다른 변수명으로 옮기거나 사용자가 직접 입력한 모든 값을 탐지하는 기능은 아니다.

TUI `/mcp`는 기존 Motifcode composer 테두리·색·선택 강조·하단 키 안내를 사용한다. 서버 선택 후 연결·해제·재연결하며 직접 `/mcp connect NAME` 명령도 가능하다. [Claude Code의 연결 상태 관리](https://code.claude.com/docs/en/mcp)와 [OpenCode의 슬래시·키보드 흐름](https://opencode.ai/docs/tui/)을 참고했다. 모델·도구가 이 관리 API를 호출할 수는 없다.

- 해제한 서버는 현재 세션에서 일시 정지되며, 다음 도구 검색이나 호출이 자동으로 되살리지 않는다.
- 설정에서 꺼졌거나 신뢰하지 않은 서버를 TUI에서 활성화할 수 없다.
- 이전 연결의 늦은 응답은 새 연결 상태를 덮어쓰지 못한다. 연결 중 취소·재연결·동시 조회·종료를 별도 테스트했다.
- 실제 실행 여부를 모르는 호출의 중복 방지 기록은 재연결이나 대화 초기화로 사라지지 않는다. 자동 재시도는 결과를 모르는 쓰기 작업을 반복할 수 없다.
- 새 대화에서는 이전 결과 핸들을 지우되 위 중복 방지 기록은 유지한다.
- 진행 중인 작업·후처리·대기 작업과 연결 변경을 겹치지 않는다. 상태 조회만 허용한다.
- Esc는 연결 **대기**를 멈춘다. 공유 연결 시작 자체는 계속될 수 있으므로 실제 해제는 `d` 또는 `/mcp disconnect NAME`을 사용한다.

## 검증 범위와 남은 제약

실제 터미널 검증은 임시 HOME, dummy credential, 소유한 JSON-RPC/SSE fixture, 빌드된 CLI, Python PTY, Chrome의 보이는 xterm.js 6.0.0으로 수행했다. OS 네이티브 터미널이나 한글 IME 조합 검증으로 표현하지 않는다. 화면 크기는 xterm과 PTY 양쪽에 적용하고 SIGWINCH를 전달했다. 40열·12행에서 패널 상단과 종료 키가 잘리는 현상을 발견하여 높이별 표시량과 폭별 키 안내를 보완했다.

이 어댑터는 tools 중심 호환이다. 다른 클라이언트의 OAuth 세션·로그인 쿠키, 모든 resources/prompts 기능, 특정 MCP 서버의 별도 정책을 자동 이전하지 않는다. 새 설정은 Motif 프로세스를 종료하고 다시 실행해야 적용된다. `/new`로 대화만 초기화해서는 적용되지 않는다. 임의의 stdio 서버를 OS 수준으로 격리하는 기능도 아니다. 작은 실험 집합에서 통과한 결과를 모든 MCP와 과제에서의 최적 속도·최소 토큰·완전한 정확성으로 확대하지 않는다.


연결 관리 기능 캠페인의 빌드 검증은 **67개 테스트 파일·952개 테스트**, 타입 검사, 도구 스키마 검사, 빌드, diff 검사를 모두 통과했다. 별도 디렉터리에 복사한 번들과 tarball 설치본을 Node **20.3.0 / 20.20.2**에서 각각 실행한 네 조합도 통과했다. stdio·HTTP의 실제 연결, 등록 시 미실행, 원문 인자 보존, 서비스 인증 참조 전달, 모델 키 미상속, CRUD와 자식 종료를 확인했다. 실제 사용 중인 전역 설치는 교체하지 않았다.

최종 화면에서는 40×12에서 제목·긴 선택 이름·상태·Esc가 보이며 120×24 복원도 확인했다. MCP 승인 후 실제 `alpha/echo` 결과, 실행 중 해제 차단과 조회 허용, Esc 취소 후 입력 복귀, 미승인 설정의 연결 차단, 정상 종료를 직접 확인했다. 캡처 9개를 보존했고 미승인 서버 시작·남은 자식 프로세스·비밀값 canary 출력은 없었다. 처음의 로컬 SSE fixture가 추가된 runtime context를 사용자 과제로 오인한 문제는 fixture에서 수정했으며 제품 결함으로 집계하지 않았다.

해당 연결 관리 캠페인에서 검증한 번들 SHA256은 `7d8d4a871b52006fafbecbe07a7cc3651e9b17bde031120effbc175da84d2159`(1,914,054바이트), tarball은 `b0241d33cc254d4d8a0838f442675f802199edcd67fb4d5143a8deb4f4cd21c7`(417,276바이트)다. 패키지·화면 검증 후 94개 소스 파일이 빌드 시점의 해시와 동일함을 확인했다. 검증 증거는 로컬 `management-usecases/`에, 공개 가능한 수치와 해시는 이 저장소의 `mcp-evaluation.json`에 기록했다.

## 추가 검증: GitHub 링크만 주고 연결 요청

사용자가 지정한 [Trendchaser-mcp](https://github.com/TaewoooPark/Trendchaser-mcp)의 `8ad13162ba64d8d836438696172a5d70e846bd72`를 검토했다. 이 주소는 HTTP MCP 접속점이 아니라 stdio 서버의 소스 저장소다. 저장소 README의 실행 명령은 GitHub 패키지를 npx로 설치하고 실행하는 방식이며, 인증 키 없이 공개 피드를 조회한다.

실제 Motif-3에 **“https://github.com/TaewoooPark/Trendchaser-mcp 이 MCP를 motifcode에 연결해줘. 연결되는지도 확인해줘.”**라고 요청했다. 빈 작업 폴더·임시 HOME에서 `motif`와 `motifcode` 모두 현재 브랜치 실행 파일로 연결했다. 20턴·79.558초 후 `turn_limit`으로 종료했고 MCP 설정은 생성되지 않았다. 모델은 주변 소스 트리를 탐색하는 데 예산을 소모했다. 더 많은 턴이나 다른 지시로도 불가능하다는 뜻은 아니지만, 현재 링크만으로 안정적으로 등록되는 경험은 확인하지 못했다.

앞선 시험에는 `motif`만 새 빌드로 연결하여 모델이 기존 전역 `motifcode`를 발견하는 환경 혼입이 있었다. 해당 실행은 브랜치의 자연어 등록 능력을 평가하는 근거에서 제외했다. `-p` 경로는 `--journal`로 도구 기록을 만들지 않아, 재시험에서는 실제 CLI의 요청/도구 결과만 외부 fetch 관찰기로 기록했다. API 키와 모델 reasoning은 기록하지 않았다.

직접 명령으로 등록한 서버의 호환성은 확인됐다. 정식 SDK를 사용하는 실제 서버로 목록·주제 상세·검색·없는 anchor 오류를 호출했고, 공개 피드를 별도 GET한 기준값과 교차 검증했다. 목록의 anchor로 상세를 읽었으며 본문·제목·원문 URL이 일치했다. 조회 도구 네 개가 정상 노출됐다.

```sh
motif mcp add trendchaser -- npx -y github:TaewoooPark/Trendchaser-mcp#8ad13162ba64d8d836438696172a5d70e846bd72
motif mcp doctor --connect
```

최초 npx 설치·빌드까지 포함하면 기본 시작 제한 10초를 넘을 수 있다. 새 HOME에서 두 번 연결에 도달하지 못했고, 사전 설치한 `node /absolute/path/to/Trendchaser-mcp/dist/index.js` 방식은 200ms에 `ready`, 도구 네 개를 확인했다. 캐시가 생긴 뒤의 npx 연결도 3.715초에 성공했다. 따라서 npx 방식 자체의 비호환으로 판단하지 않는다. 첫 연결이 느릴 때는 검토한 소스를 미리 설치·빌드하고 절대 경로로 등록하거나 설정 파일의 `startupTimeoutMs`를 명시적으로 조정한다.

이 과정에서 **doctor가 `connecting` 상태와 도구 0개인데도 exit 0을 반환하는 실제 결함**을 발견했다. 공유 연결 시작이 계속되는 동안 조회 대기만 시간 초과한 경우였다. 이제 모든 활성 서버가 `ready`일 때만 성공하며, 그렇지 않으면 `connection_not_ready`와 exit 1을 반환한다. 도구가 실제로 0개인 정상 `ready` 서버는 계속 성공한다. 수정 후 새 HOME의 동일 npx 시험은 12.104초 뒤 올바르게 실패했고, 사전 설치 서버는 정상 성공했다. 회귀 테스트를 포함한 **67개 파일·954개 테스트**, 타입 검사·스키마 검사·빌드를 통과했다. 위 952개 테스트와 artifact 해시는 이 수정 이전 캠페인의 기록이다.

정상 등록한 서버를 새 모델 세션에 제공하자 Motif-3는 29.805초·모델 요청 네 번으로 목록→브리프→주제 상세를 실제 MCP로 조회했다. 날짜·slot·anchor·headline은 정확했고 native 도구로 우회하지 않았다. 다만 요청한 두 문장 요약을 실제로 쓰지 않고 “요약했다”고만 답했으므로 **도구 기능은 통과, 전체 과제 이행은 미달**이다. 자동 채점의 문자열·도구 검사는 통과했으나 독립 의미 검토에서 이를 바로잡았다. 브리프 전체 읽기도 요청한 목록→주제 조회에 비해 추가 한 번이었다.

이 최초 검증에서는 등록 절차를 모델에게 안내하는 설치 흐름이 필요하다고 판단했다. 아래 실험에서 내장 스킬로 이를 보완했다. 설정의 동적 추가는 아직 구현하지 않았다. `/mcp`는 시작 시 등록된 서버의 연결 관리이며, 새 설정은 프로세스 재시작으로 적용한다. 이 검증에서는 사용자 전역 설치와 실제 MCP 설정을 변경하지 않았다.

## 내장 mcp-setup와 자연어 등록 검증

2026-09-26 KST 기준, `mcp-setup`을 16번째 기본 스킬로 추가했다. 원래 사용자 입력에 URL·MCP·명확한 설치 요청이 함께 있으면 기존 스킬 렌더러로 본문을 한 번 첨부한다. TUI·print·단일 과제에 적용하며, 설명 요청·거절·인용문·첨부 파일에서 발견한 문장은 제외한다. `/mcp-setup <URL>`로 명시할 수도 있다. 사용자·프로젝트 스킬 우선순위, 본문 예산, 실행 권한은 기존 체계를 따른다. 재개된 기록에는 중복 첨부하지 않는다. 시스템 프롬프트나 도구 목록에 별도 라우터를 추가하지 않았다.

스킬은 설치된 CLI 확인 → 기존 등록 확인 → 서버 README·manifest 확인 → 문서의 실행 명령으로 등록 → 실제 `doctor --connect`의 `ready` 확인 순서다. GitHub URL을 HTTP 접속점으로 오인하지 않도록 구분한다. 문서에 `npx`·`uvx` 명령이 있으면 우선 사용하고, npx 최초 설치는 미리 준비해 짧은 연결 제한과 분리한다. 직접 소스 빌드는 문서 명령을 사용할 수 없을 때의 대안이다. 정상 연결 후에는 수동 JSON-RPC나 업무 도구 호출로 설치 과제를 늘리지 않도록 안내한다.

연결 성공과 절차 품질은 구분했다. 두 GitHub 시험의 실제 npm 캐시는 검토한 `8ad13162…`/v0.1.0이었지만, 모델은 저장 명령에 SHA를 고정하지 않았다. 따라서 미래 설치의 동일 버전을 보장하지 않는다. seed 101은 불필요한 explicit config 때문에 한 번 실패한 뒤 정상 진단으로 해소했고, seed 102는 필수 재시작을 “새로고침이 필요할 수 있다”고 약하게 안내했다. **새 등록 적용에는 Motif 프로세스 종료·재실행이 필요하며 `/new`·`/mcp`로는 부족하다.** HTTP 시험은 이 안내가 정확했지만 불필요한 HEAD·GET 요청 두 번이 있었다.
